# 工作流 Key 与计费：现状核对和实施计划

日期：2026-10-28。以下为第 0 阶段核对与原始实施计划，未验证线上 sub2api 版本与真实计费。

最新本地进度：工作流经 Bridge 走 sub2api 网关的 `per_request` 扣费（假模型调用），不需要修改 sub2api 源码，也不直连计费数据库；任务成功才扣费，失败/取消不扣费。原来的 `:18083` 计费 fixture、冻结表和逐组件明细已撤回。访客发现页和独立多 Key 管理也已接入。最新状态见 [本地测试架构](LOCAL-TEST-ARCHITECTURE.md) 和 `CYAPI-toolbox/server/bridge/README.md`；下文“尚未启动/尚未接通”等描述保留为早期核对记录。

## 1. 范围

工作流独立使用用户的 CYAPI API Key，覆盖模板、价格确认、任务、结果和费用记录。工具接入及各工具的 Key、配置和登录完全独立，不读取、不复用、不迁移，也不改变现有行为。

首个目标为一个固定价格的图片工作流，先使用模拟上游和测试余额验证，真实模型、价格和付费测试预算另行确认。不在本阶段部署、调用真实付费接口或改动用户余额。

## 2. 已核对的本地现状

以本地代码为证据，不代表线上部署版本已经核实：

| 项目 | 现状和证据 |
| --- | --- |
| 工作流入口 | 客户端 `docs/WORKFLOWS.md` 描述远程工作台，业务页面位于服务端 `server/workflows/public/`；桌面远程 WebView 无原生 IPC 权限。 |
| 身份验证 | `server/workflows/auth.mjs` 固定调用 `https://www.cyapi.cyou/v1/usage`；验证成功后丢弃原始 Key，会话只有 Key HMAC 归属、CSRF 和 30 分钟有效期。usage 响应中的余额等字段用于识别响应，并未作为可用余额向业务层返回。 |
| 数据归属 | 工作流资料以持久 secret 派生的 Key HMAC 隔离；`server/workflows/store.mjs` 按 owner 存 JSON。相同 Key 可恢复历史，更换 Key 不合并；身份 secret 与数据必须一起备份。 |
| Key 吊销 | 已签发会话不随 Key 吊销立即失效；Bearer 模式每次实时验证。 |
| 执行 | `server/workflows/engine.mjs` 只执行模拟图，任务意图先保存，草稿重复启动返回原任务；提交不确定时不自动重试。服务重启时活跃任务变为 interrupted，不恢复追踪。 |
| 限制 | owner 锁仅在单进程内，文件状态与外部余额系统不在同一事务；该实现不能直接充当多进程或跨服务资金事务。执行中的超时、重启和结果收集失败也不等同于上游未产生费用。 |
| 测试 | 2026-10-28 本地运行 `node --test tests/workflows.test.mjs`，6 项通过；使用 fixture Key 和模拟引擎，不代表真实 Key、线上服务或计费已验收。该测试不在 server `npm test` 脚本列表中，需显式执行。 |

**关键缺口：**浏览器会话不能从 HMAC 恢复 Key。真实任务需要安全的调用授权方案；不能假设登录完成后后台已能代表 Key 付费。不得把 Key 放进图、分享文件、URL、日志、任务 JSON 或 ComfyUI 元数据，也不能为此放宽远程 WebView 的桌面 IPC 权限。

## 3. sub2api 需确认事项

尚未核对生产部署的 sub2api 版本。计费草案 `MULTIMODAL-BILLING-BRIDGE.md` 的源码推论与 M0/M0.5 状态存在混用，均不能当成生产实测结果。只读查看公开仓库 main 的 `backend/internal/handler/admin/user_handler.go` 可见余额调整入口及幂等包装，但这不是部署版本证据，也不能证明支持资金预留、余额并发约束、长期幂等或用户可见消费账单。

更新：用户提供本地源码 `F:/codex_prj/CYAPI/sub2api`，但线上部署版本仍未知。`backend/internal/handler/gateway_handler.go` 的 `/v1/usage` 有 Key 配额、订阅及钱包等不同模式，不能把每种 remaining 当成钱包余额；处理内部可见 user ID，但不能据此认定响应公开稳定身份。`backend/internal/repository/user_repo.go` 的普通 `DeductBalance` 明确允许透支；`backend/internal/service/admin_user.go` 使用原子余额调整，但调整记录创建失败只记日志。现有原生用量计费另有事务与去重实现，是否适合工作流异步预留和结算仍需专项验证。

部署方向调整：工作流业务和执行引擎维持逻辑与进程边界，当前仍统一部署远端；分机和 FRP 留待后续，不提前放开引擎访问范围。

计费方向调整：用户选择异步任务由 Bridge 维护任务及计费状态，sub2api 是唯一真实余额来源。提交前预留，明确成功后结算，明确失败或确认取消后释放；Bridge 的记录不是另一套钱包。余额冻结必须由 sub2api 或与其所有消费共享的权威账务能力原子执行，仅预检或 Bridge 内标记冻结都不够。超时、取消请求发送后或通信失败不能证明上游停止；状态未知时保留待核对，不能立即释放或重试。结算/释放响应丢失要通过幂等操作 ID 查询对账，不能盲目重复。记录 0 元失败流水只表示用户未扣款，不代表上游没有成本。

首版只实现不连接真实余额的计费状态机及测试；还未接入工作流任务、未实现冻结、扣款、释放或账单。已有固定测试积分报价也不是用户余额或最终售价，真实报价需由权威价格配置支持并与结算一致。

本地 sub2api 源码还存在批量图片专用的余额预留、结算和释放：`backend/internal/repository/usage_billing_repo.go` 中预留以数据库事务将可用余额转入 `frozen_balance`，操作使用请求去重；`backend/internal/service/batch_image_billing_hold.go` 和相关批量任务服务负责调用。它是复用候选而非现成的工作流 API：仍需评估每任务冻结归属、结算与释放互斥、订阅/Key 限额、缓存失效、审计和崩溃恢复，不能直接暴露内部函数。

本地联调准备：`server/tests/fixtures/mock-openai-images.mjs` 是只监听回环的 OpenAI 形态图片假上游，返回静态 PNG 或可控失败，不连接任何真实模型；它目前没有与 sub2api 或工作流连接，也不验证余额。完整隔离的 sub2api 测试环境尚未启动；检查时缺少 Docker 和 PostgreSQL，Go 版本也低于仓库要求，必须先准备依赖。

必须基于实际部署版本或测试环境确认：

1. Key 校验结果是否能安全返回稳定 user ID、key ID、状态、分组和权限；usage 中各余额/配额字段的含义、单位和准确性。
2. 现有原生请求计费与图片通道的支持范围、账单形态；同步/异步的成功、失败、超时、取消如何计费。
3. 是否存在原子预留、结算、释放、余额不足拒绝、与其他业务并发消费协调的接口；幂等键作用域与保留时长、超时查询、账单和审计行为。
4. 服务间授权、权限最小化和吊销；不要仅因 admin balance API 存在就直接用于生产扣款，也不要通过两个系统各自检查余额来保证不超扣。
5. 一条图片上游的模型、协议、参数、价格、幂等和查询能力，及测试预算。

## 4. 拟定实施顺序和验收

### P0：确定契约与授权方案

- 确认实际 sub2api 版本、接口和第一条图片产品。定义产品和价格版本、报价过期策略、任务 ID、请求幂等键、状态、账单和错误语义。
- 比较可行的调用授权方式：例如受限短期服务令牌，或经安全审查的短期凭据保管；凭据的生命周期、服务重启、退出、吊销和异步任务继续执行分别定义。若无法取得可用授权能力，暂不实现真实付费。
- 评估稳定用户身份；在确认前保留现有 Key HMAC 隔离。未来跨 Key 合并历史需要经过用户归属证明、迁移和回滚设计，不能自动按猜测合并。
- **验收：**形成带证据的接口清单和明确的授权/计费决策；未验证项标记阻塞。

### P1：模拟报价与任务契约

- 工作流页面增加明确的模拟报价及确认交互，模拟价、余额和费用必须标为测试数据，不能冒充真实账单；现有免费模拟路径保持可用。
- 服务端采用可注入的模拟产品、计费和上游接口，测试任务与报价版本绑定、重复提交、失败和未知状态；不得访问真实余额。
- **验收：**取消确认不发起任务；同一提交只建立一个任务；金额、任务状态与测试账单匹配；权限和现有模拟测试不回归。

### P2：生产计费能力与持久化

- 选定唯一余额权威来源。支持原子预留/结算/释放或证明其他机制与所有并发消费一致；价格、货币、精度、费用快照和流水采用明确规则。
- 任务持久化和可靠幂等需覆盖多进程、崩溃、重复回调及跨服务部分成功；由对账与人工处理解决无法自动判断的状态。不能只依赖现有进程锁、文件状态或上游请求超时。
- 上游已接受但响应丢失时维持待核对，不自动重提或切换线路；取消是否收费依据已核对的上游和产品规则，不承诺一定退款。
- **验收：**并发余额、重复请求、重启、响应丢失、账务异常与对账通过，任何失败均可追踪，不能重复扣费。

### P3：一条真实图片链路与灰度

- 接入一个核对过的图片接口；先用模拟依赖完成端到端验证，再经用户确认模型和预算进行少量真实调用。
- 页面展示真实价格、明确确认、真实任务状态、结果和可解释费用；不从成功的登录推测余额。
- 增加隔离、限流、审计、告警、备份和回滚方案；上线部署另行确认。
- **验收：**一次经授权的真实生成及账务对账，重复提交、未知状态和结果访问隔离通过。
